3. 📦 Проект №1 — WEB

3.1. Назначение и границы

Shop.Web показывает каталог, проверяет цены и остатки, создаёт заказ, инициирует оплату и предоставляет кабинет покупателя и оператора. Бухгалтерия, складская логистика и обработка карточных реквизитов остаются за границей системы. Корзина хранится в браузере; при оформлении сервер заново проверяет все позиции.

3.3. Архитектурный стиль

Слоистый модульный монолит: каталог, заказы, идентификация и интеграции имеют отдельные сервисы, но общий релиз и транзакционную БД. Это позволяет атомарно резервировать товар и создавать заказ без распределённой транзакции. Выделение микросервисов рассматривается только при независимых командах или подтверждённой потребности в отдельном масштабировании.

Инварианты оформляются в сервисах Web; строгая инверсия зависимостей потребует отдельной общей сборки.

3.7. Аутентификация и авторизация

Cookie-сессия: Secure, HttpOnly, SameSite=Lax; срок 8 часов, проверка блокировки аккаунта не реже 5 минут. Хэширование пароля через PasswordHasher; MFA обязательно для операторов и администраторов. Ключи Data Protection общие для реплик и сохраняются в защищённом томе.

3.8. Асинхронная обработка

Транзакционный outbox вместо отдельного брокера. Заказ и событие письма записываются атомарно. BackgroundService опрашивает события раз в 2 секунды; несколько воркеров используют FOR UPDATE SKIP LOCKED и аренду на 60 секунд. Доставка at-least-once: получатель дедуплицирует event_id. Retry 5/30/120/600/1800 секунд с jitter; после 10 неудач — dead letter и оповещение. Планировщик каждые 60 секунд отменяет неоплаченные заказы старше 30 минут и освобождает резерв в транзакции.

3.9. Кэширование

In-memory cache: карточки и первая страница каталога, TTL 30 секунд, ограничение 64 МБ на реплику. После изменения локальная запись удаляется; другие реплики обновятся по TTL. Финальная цена и остаток всегда читаются из БД. Статика с хэшем имени: Cache-Control max-age=31536000, immutable. Персональные ответы: no-store. CDN и Redis в базовом варианте не используются.

3.10. Ошибки и логирование

Структурированные JSON-логи: timestamp UTC, level, eventId, traceId, spanId, route, durationMs; без паролей, cookie, адресов и полного тела запроса. Information — операции; Warning — конфликты и временные сбои; Error — необработанные ошибки. Middleware выдаёт безопасный ProblemDetails, подробности остаются в логах. W3C traceparent связывает вызовы.

HTTP timeout 5 секунд, до двух повторов только безопасных или идемпотентных операций, backoff 200/800 мс с jitter. Circuit breaker внешнего провайдера: после пяти последовательных сбоев пауза 30 секунд, затем пробный запрос. Отмена запроса передаётся вниз. Запись в БД повторяется только целой транзакцией с тем же ключом.

3.11. Конфигурация и секреты

Обычные параметры — appsettings и переменные окружения. ConnectionStrings__Shop, Payments__SigningKey и Email__ApiKey поступают из {{SECRET_MANAGER}}; локально — user-secrets. Валидация конфигурации при старте. Ротация через перекрывающиеся ключи; секреты и строки подключения не попадают в Git, логи или HTML.

3.12. Развёртывание

Dev — локальные контейнеры и синтетические данные; stage — отдельная БД и sandbox оплаты; prod — две Web-реплики и отдельный Worker. OCI-образ собирается многоэтапно, процесс без root. Пайплайн: restore → build → unit → integration → анализ зависимостей → сборка и сканирование образа → stage → e2e → согласование prod → миграции отдельным job → rolling deploy → smoke. Образ фиксируется digest; миграции не выполняются каждой репликой при старте.

3.13. Тестирование

Целевая пирамида: 70% unit (xUnit: деньги, переходы статусов), 20% integration (Testcontainers PostgreSQL: FK, миграции, конкуренция заказов), 10% e2e (Playwright: вход, покупка, права, webhook). Цель покрытия бизнес-правил ≥ 80%; это не измеренное текущее покрытие. Обязательные сценарии: две покупки последнего товара, повтор POST, поздняя оплата отменённого заказа и восстановление из backup. k6 проверяет нагрузочные бюджеты.

4.5. Нормализация

Основные сущности приведены к 3НФ. Снимки названия, SKU и цены в order_items — исторические факты, которые не меняются вместе с каталогом. total — сознательная денормализация для списка заказов; сверяется при записи. JSONB используется только для версионированных интеграционных событий.

4.6. Индексы и производительность

Индексы из §4.4 обслуживают каталог, историю покупателя, выбор неоплаченных заказов, joins и очередь. PK и UNIQUE создают собственные индексы; PostgreSQL не создаёт индекс на каждом FK автоматически. Поиск по названию первоначально ограничен префиксом; полнотекстовый GIN — отдельное улучшение после измерений.

EXPLAIN (ANALYZE, BUFFERS) выполняется на stage с репрезентативными данными: проверяются actual/estimated rows, чтения, сортировки и p95. ANALYZE действительно исполняет запрос; изменяющие запросы исследуются только в безопасной тестовой базе. Autovacuum включён, N+1 исключается проекциями.

4.7. Транзакции и целостность

READ COMMITTED, короткие транзакции. При оформлении товарные строки блокируются FOR UPDATE в порядке UUID; остаток уменьшается только при достаточном количестве. Создание заказа, позиций и outbox атомарно. При конфликте уникального ключа вся транзакция откатывается; существующий заказ читается и сравнивается request_hash. Административные изменения используют version и WHERE version = expected.

Отмена и webhook блокируют строку заказа. Отмена освобождает резерв только при переходе pending → cancelled. Оплата отменённого заказа не возвращает его в paid: создаётся событие refund_required. Повтор webhook не изменяет остаток. Deadlock/serialization failure допускает два повтора всей транзакции. ACID обеспечивается PostgreSQL при fsync и synchronous_commit=on; асинхронная реплика сама по себе не гарантирует нулевую потерю данных.

4.8. Миграции

EF Core, имя YYYYMMDDHHMM_КраткоеНазвание, миграция и ModelSnapshot в одном коммите. Forward-only; rollback приложения допустим, пока схема совместима. Expand → backfill пакетами → переключение кода → contract в следующем релизе. SQL проверяется на stage, задаются lock_timeout 2 с и отдельный лимит выполнения. CREATE INDEX CONCURRENTLY запускается вне транзакции. Перед разрушительной миграцией — проверенный backup и план восстановления.

4.9. Резервное копирование

Ежедневный физический base backup, непрерывная архивация WAL с archive_timeout 60 с; удержание 14 суток. Еженедельный логический dump — дополнительная переносимая копия. Копии шифруются и хранятся в отдельном аккаунте с неизменяемым сроком хранения. Цели RPO ≤ 15 минут и RTO ≤ 60 минут подтверждаются ежемесячным PITR в изолированную среду: восстановить base backup, проиграть WAL до точки, проверить контрольные суммы и сценарии заказов, записать фактическое время.

4.10. Безопасность БД

shop_app: SELECT/INSERT/UPDATE на необходимые таблицы, без DDL; shop_worker — outbox и необходимые чтения заказов; shop_migrator — DDL только на время релиза; backup-роль отдельно. БД в закрытой сети, TLS с проверкой CA и имени сервера. At-rest — шифрование дисков и backup средствами инфраструктуры. Аудит DDL и привилегированных операций собирается централизованно. Stage получает синтетические данные, email и адреса в выгрузках маскируются. Удаление PII выполняется по {{RETENTION_POLICY}} с учётом требований хранения заказов.

4.11. Масштабирование

Сначала вертикальное масштабирование и оптимизация запросов. Для высокой доступности — primary и standby с управляемым failover и fencing старого primary. Чтения после записи идут на primary; отчёты могут использовать replica с контролем lag. Шардирование не требуется. Партиционирование старых заказов по месяцам рассматривается при подтверждённых объёмах; оно требует пересмотра PK/UNIQUE и FK, поэтому не включено в текущую модель.

4.12. Мониторинг

Метрики: активные соединения, ожидания блокировок, deadlocks, cache hit, disk/WAL, autovacuum, replication lag, возраст последнего backup. Slow query log от 500 мс без персональных параметров; pg_stat_statements для агрегатов. Алерты: диск > 80% 10 минут, соединения > 80% 5 минут, lag > 30 с 5 минут, WAL не архивируется > 5 минут, backup старше 26 часов. Дежурный: {{ON_CALL}}.

EF Core используется для типизированных запросов, отслеживания изменений и миграций. AsNoTracking и Select применяются к чтению. Параметризованный SQL нужен для блокировок остатков и SKIP LOCKED; конкатенация входного SQL запрещена. DbContext scoped, не разделяется между потоками.

Один NpgsqlDataSource на процесс; пул максимум 30 соединений × 2 Web + 10 Worker = 70, бюджет PostgreSQL 100 с резервом для эксплуатации. Отказ БД возвращает 503; retry записи учитывает неоднозначный результат commit и Idempotency-Key.

-- CRUD: резервирование внутри транзакции оформления
UPDATE products
SET stock = stock - @quantity, version = version + 1
WHERE id = @product_id AND stock >= @quantity
RETURNING id, price, currency;
-- Ноль строк: откат всех позиций, HTTP 409.

-- Отчёт продаж: даты параметризованы; отменённые заказы исключены
SELECT date_trunc('day', created_at AT TIME ZONE 'UTC') AS day,
       count(*) AS orders_count, sum(total) AS revenue
FROM orders
WHERE status IN ('paid', 'shipped')
  AND created_at >= @from AND created_at < @to
GROUP BY 1 ORDER BY 1;

Создание: заказ + позиции + резерв + outbox. Чтение: каталог и свои заказы проекциями. Обновление: версия товара или переход статуса. Удаление: архивирование товара, очистка обработанного outbox спустя 30 дней; персональные данные — по политике хранения. Отчёт показывает продажи по дате создания заказа, а не денежные поступления по дате оплаты.

6. 🔐 Сквозные аспекты

Безопасность

Контроль рисков OWASP Top 10: object-level authorization, параметризованный SQL, кодирование HTML, запрет массового связывания моделей, анализ зависимостей. HTTPS/HSTS; CSP с nonce для inline-скриптов приложения. CORS закрыт по умолчанию. Cookie-запросы изменения требуют CSRF; webhook вместо CSRF требует подписи, проверки timestamp и дедупликации.

Лимиты: каталог 120/мин на IP; вход 10/мин на IP и аккаунт; оформление 10/мин на аккаунт. Общий лимит между репликами обеспечивает шлюз. Внутренние health/metrics доступны только эксплуатационной сети.

Наблюдаемость

JSON logs, OpenTelemetry traces и metrics с экспортом в {{OBSERVABILITY_BACKEND}}. traceId попадает в безопасный ответ ошибки. Метрики не используют userId или orderId как labels. Сбор: latency, error rate, pool wait, возраст outbox, процент успешных оплат.

Производительность

Бюджеты: p95 БД ≤ 100 мс, application ≤ 200 мс для каталога; Web CPU < 70% при целевой нагрузке. Каталог ≤ 2 SQL-запросов на страницу. Ошибки и исключения SLO определяются в {{SLO_POLICY}}; фактические значения подтверждаются нагрузочным тестом.

Отказоустойчивость

При потере Web-реплики балансировщик направляет новые запросы на здоровую. При потере БД запись останавливается до failover; клиент повторяет оформление с прежним ключом. При отказе почты outbox удерживает события. При отказе оплаты заказ остаётся pending до истечения резерва; платёжный статус сверяется после восстановления.
